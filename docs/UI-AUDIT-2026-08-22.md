## Corrections from measurement — added 2026-08-22, after the findings below

The findings below were later measured in a real browser. Most held. These did
not, and they are recorded here rather than only in the fixes, because a reader
who cherry-picks one finding out of this file will not see the commit that
contradicts it.

**🔴 `[medium / certain]` "the h1 ellipsis half is pure correctness and can land
alone" is FALSE, and following it makes the page worse.** Measured at 360px with
headless Chromium: baseline 107px of clipped overflow; with the h1 ellipsis rule
alone, **262px** — two and a half times worse. `white-space:nowrap` converts the
title from a wrapping box into an unbreakable min-content floor, and on a track
still sized to `max-content` that floor propagates straight into the column. The
ellipsis is only safe once `grid-template-columns:minmax(0,1fr)` caps the track.
The two ship together, and did, in `8bbfbae`. This is the finding most likely to
be picked up alone, because the sentence explicitly invites it.

**`.conversation-shell{min-width:0}` was never going to help, and it was already
in the file.** Measured 107px before and after at 360px. `.messages` is a column
flex container, so `min-width:auto` is not the shrink floor on the horizontal
axis; the grid track was.

**The `env(safe-area-inset-bottom)` observation understates itself.** The audit
notes `.side-foot` is the only use of `env()` in the tree. Measured, that one use
never applied either — `30-workspace.css` re-declares `.side-foot` and loads
later. So the codebase had no notch handling at all, not one instance on the
wrong element. Fixed in `a730834`.

**The dead-mobile-rule mechanism is a pattern here, not a one-off.** The audit
found it on `.composer-shell`. The same mechanism was later measured on
`.workspace-view` (declared `18px`, computed `34px` on a 360px phone) and
`.side-foot`. Any rule in `10-shell.css`'s media blocks whose selector is
re-declared unconditionally in `20-`, `30-` or `35-` is dead: media queries add
no specificity, so at equal specificity source order decides.

**Composer gutter: the obvious repair is harmful.** Making the dead
`.composer-shell{padding:8px 16px 14px}` apply aligns 640px and makes 720px and
768px worse (−24.4px → −34.4px of misalignment), because `.messages` above 640px
is on `max(24px,7vw)`, not a flat 16px. The `--gutter` token in this file's own
proposal is the correct fix and measures 0 at every width.

## [high / certain] `/home/example/code/trio/server/web/js/11-conversation.js` — 768-788 (upsert)

**Problem.** Per-message forced synchronous layout during the history prime burst, plus an O(n^2) sibling scan. 04-events.js:44 fans a primed history array out as one SSE 'message' event per message (`payload.messages.forEach(dispatch)`), so `upsert()` runs once per message, up to the 500 held by `pruneMessages(limit = 500)`. Each run is read -> write -> read -> write against the live list: `nearBottom(dom())` reads scrollHeight/scrollTop/clientHeight, `list.insertBefore/append` writes, then `list.scrollTop = list.scrollHeight` reads layout again and writes. That is one full forced relayout of the whole growing flex column per message. On top of it, `[...list.children].find(...)` materialises a fresh array of every card already painted and scans it, and `markRead()` calls `ordered()` (Map spread + sort) then `flushRead()` calls `ordered()` a second time and iterates all of it. Fermi: 500 forced layouts of an average 250-node markdown-bubble flex column; ~2-4 ms each on desktop, 4-6x that on a mid-range phone -> 1-7 s of blocked main thread on channel open. This is the one finding that is an order of magnitude worse on the phone than on the desktop the operator is not complaining about.

**Evidence.** line 768 `const wasNear = nearBottom(dom());` ... line 780 `const nextSibling = [...list.children].find(el => el.dataset?.messageId && Number(el.dataset.messageId) > Number(msg.id));` ... line 786 `if (wasNear && list) { list.scrollTop = list.scrollHeight; markRead(); }` — and `nearBottom` is `el.scrollHeight - el.scrollTop - el.clientHeight < 80` (line 81), a layout read.

**Proposed fix.** Batch the burst instead of touching the DOM once per message. Add a module-level `let pendingCards = null, pendingRaf = 0;`. In `upsert`, when `!existing`, build the card and push it to `pendingCards` (a DocumentFragment) rather than inserting; replace the `[...list.children].find(...)` ordering scan with a comparison against the last inserted id (fall back to the existing scan only when `Number(msg.id)` is lower than the last id, which is the rare out-of-order case the comment guards). Then schedule once: `if (!pendingRaf) pendingRaf = requestAnimationFrame(flushPending)`, where `flushPending` does a single `list.append(pendingCards)`, a single `if (wasNear) list.scrollTop = list.scrollHeight`, a single `markRead()`, a single `pruneMessages()`, and clears `pendingRaf`. Hoist the `wasNear` read to the top of the burst (capture it when `pendingRaf` is first scheduled) so no layout read happens after a write.

## [high / certain] `/home/example/code/trio/server/web/css/10-shell.css` — 899-907 (@keyframes ripple / rippleUrgent)

**Problem.** Both status-ring keyframes animate `box-shadow`, a paint property, with `infinite` iteration. The browser repaints the ring on every frame for as long as any agent is working, compacting, spawning or blocked — which in an agent coordination workspace is most of the time. Up to four of these live in the header face-pile (20-workspace.js:349 `members.slice(0, 4)`), and the header is `.conversation-header`, which carries `backdrop-filter:blur(8px)`. A continuously repainting child forces that full-width blurred layer to re-raster every frame, which is the expensive combination on a mobile GPU. The keyframes convert to compositor-only properties with no visual change: the effect is a ring growing outward and fading, which is exactly scale + opacity.

**Evidence.** line 899 `@keyframes ripple{ from{ box-shadow:0 0 0 0 color-mix(in oklab,var(--c) 55%,transparent); } to { box-shadow:0 0 0 4px color-mix(in oklab,var(--c) 0%,transparent); } }`, applied at line 874 `.st-working .st-ring, .st-compacting .st-ring, .st-spawning .st-ring{ animation:ripple var(--pulse-busy) var(--ease) infinite; }`

**Proposed fix.** Move the halo to a pseudo-element and animate transform/opacity. Give `.st-ring` `position:relative` and add `.st-ring::after{ content:""; position:absolute; inset:0; border-radius:inherit; box-shadow:0 0 0 4px var(--c); opacity:0; }`. Rewrite the keyframes as `@keyframes ripple{ from{ transform:scale(1); opacity:.55 } to{ transform:scale(1.55); opacity:0 } }` and `@keyframes rippleUrgent{ from{ transform:scale(1); opacity:.75 } to{ transform:scale(1.7); opacity:0 } }`, and retarget lines 874-879 to `.st-working .st-ring::after` etc. Both properties are compositor-only, so the ring animates off the main thread. Keep the existing `prefers-reduced-motion` overrides at 884-890 pointed at the same `::after`.

## [high / certain] `server/web/css/20-conversation.css` — 233 (`.composer-shell`), vs 226 (`.messages`)

**Problem.** The message column and the composer below it use different horizontal gutters, so on a phone the input box is inset 10px further than the bubbles it sits under — the two edges the eye tracks most on a narrow screen don't line up. **Evidence.** L226 `.messages{gap:0;padding:22px max(24px,7vw) 10px}` + L227 `@media(max-width:640px){.messages{padding-left:16px;padding-right:16px}…}` versus L233 `.composer-shell{border-top:0;background:var(--bg);padding:8px 26px 20px}` — a bare `26px` with no breakpoint. Note that `body.compact` never broke: L115 `body.compact .messages{padding:14px clamp(12px,3vw,40px)…}` and L116 `body.compact .composer-shell{padding:8px clamp(12px,3vw,40px) 12px}` still share one expression, as did the pre-redesign defaults at L2 and L197 (both `clamp(16px,4vw,52px)`). **Proposed fix.** Give the gutter a name and use it in both places. In `00-tokens.css` `:root` (next to the spacing rhythm at L19-20) add `--gutter: max(24px, 7vw);`. Then `20-conversation.css` L226 becomes `padding:22px var(--gutter) 10px`, L233 becomes `padding:8px var(--gutter) 20px`, `.private-banner` (also L226 block, currently `padding:0 26px`) becomes `padding:0 var(--gutter)`, and the now-redundant `.messages{padding-left:16px;padding-right:16px}` inside L227's media query is deleted. This changes `.messages` at no width — the value is identical — so desktop is pixel-identical; only the composer moves, and it moves onto the message column's gutter.

**Problem.** An infinite animation on `background-position` — a paint property, never compositable — applied to an element that also uses `background-clip: text`. ## [medium / certain] `/home/example/code/trio/server/web/js/11-conversation.js` — 858 (onScroll)

**Problem.** The scroll handler is unthrottled and does two full sorts of the message Map on every scroll event. `markRead()` (line 129) calls `ordered()`, and then `flushRead()` (line 133) calls `ordered()` again and iterates the whole result. `ordered()` is `[...state.messages.values()].sort(...)` — a 500-element array allocation plus an n log n sort with a `Number()`-coercing comparator, twice, per event. Chrome Android fires scroll events at up to display rate during a fling, and the operator sits at the bottom of a chat, which is exactly where `nearBottom` is true and this path runs. Fermi: 500 * log2(500) ~ 4500 comparisons per sort, 2 sorts, ~50-100 ns per closure call on a mid-range phone -> 0.5-1 ms per frame, plus two 500-element allocations per frame driving minor GCs during the fling. That is 3-6% of a 16 ms budget burned to recompute a value that has not changed.

**Evidence.** line 858 `const onScroll = () => { jump.classList.toggle('hidden', nearBottom(list)); state.scrollPositions[convId()] = list.scrollTop; if (nearBottom(list)) markRead(); };` with line 672 `function ordered() { return [...state.messages.values()].sort((a, b) => Number(a.id) - Number(b.id)); }`

**Proposed fix.** Two changes. (1) rAF-throttle the handler: `let scrollRaf = 0; const onScroll = () => { if (scrollRaf) return; scrollRaf = requestAnimationFrame(() => { scrollRaf = 0; const near = nearBottom(list); jump.classList.toggle('hidden', near); state.scrollPositions[convId()] = list.scrollTop; if (near) markRead(); }); };` — this also collapses the duplicated `nearBottom` call into one. (2) Memoise `ordered()`: keep `let orderedCache = null;` at module scope, return it when non-null, and set `orderedCache = null` in `upsert()` and `pruneMessages()` (the only writers of `state.messages`). Register the listener with `{ passive: true }` while you are there.
