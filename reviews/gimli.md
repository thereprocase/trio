### Gimli — Sonnet

**Findings:**

1. **[critical]** `setup.sh:144` — Python one-liner inlines a bash array expansion into a Python heredoc via shell substitution. The `$(printf '%s\n' "${TRIO_TOOLS[@]}" | "$PYTHON_CMD" -c "...")` construction spawns a second Python process mid-script just to JSON-encode a string list. This is brittle: if `$PYTHON_CMD` is not in PATH at that exact moment, or if the inner process fails silently, `tools` becomes `None` in the outer Python script and crashes without a useful error. Simpler: build the JSON list directly in bash using `printf` and embed it as a literal string, or consolidate the whole allowlist step into a standalone Python script that constructs the list itself. The two-process pipeline for list serialization is a fragile construction.

2. **[critical]** `setup.sh:144` — The `settings_path` variable is embedded via bare shell interpolation (`'$SETTINGS_JSON'`) inside single-quoted Python source. Single quotes in bash prevent variable expansion, so `$SETTINGS_JSON` is passed as a literal string to Python — it never expands. This means `settings_path` will literally be the string `$SETTINGS_JSON` and `os.path.exists(settings_path)` will always be False. The allowlist step silently creates a new `settings.json` at a path named `$SETTINGS_JSON` rather than the real one. **This bug means the allowlist step always fails silently.**

3. **[warning]** `setup.sh:85` — The fallback `sed`-based Windows path conversion (`echo "$SERVER_SCRIPT" | sed 's|^/\([a-zA-Z]\)/|\1:\|' ...`) only handles single-letter drive roots like `/c/Users/...`. It fails on UNC paths (`//server/share/...`) and produces broken output for paths with spaces when passed unquoted to `claude mcp add` on line 108. The `cygpath` branch handles this correctly, but the sed fallback is present specifically for environments without `cygpath` — exactly the environments most likely to be fragile.

4. **[warning]** `setup.sh:27-29` — Python version check is missing. The script finds `python3` or `python` and reports the version string, but never parses or enforces the 3.10+ requirement stated in the comment. A Python 3.8 environment will pass the check, install `mcp`, then fail at import time with a cryptic `TypeError` because `Path | None` union syntax (used extensively in `trio_server.py:118`) requires 3.10+. The check should parse `sys.version_info` and `exit 1` with a clear message.

5. **[warning]** `setup.sh:65` — `trio_wait.py` is copied unconditionally with no existence check (compare: `SKILL.md` gets a guarded copy at line 59). If `trio_wait.py` is missing from the source tree, `set -euo pipefail` causes a silent abort with no diagnostic. Should mirror the SKILL.md pattern or at minimum add an existence guard with an error message.

6. **[warning]** `setup.sh:106-108` — `claude mcp remove` is called with `2>/dev/null || true` which silences all errors including unexpected ones. `claude mcp add` output is captured with `2>&1` and printed, but there is no check on exit code. If `claude mcp add` fails (e.g., permission error, malformed path), setup reports success and the user is left with an unregistered server and no indication of failure. Should capture exit code separately and fail loudly.

7. **[warning]** `server/trio_server.py:458-522` — `trio_poll` holds an open SQLite connection across a polling loop that sleeps 2 seconds per iteration (up to 30 seconds total). Each MCP session spawns its own server process, and with N participants polling simultaneously, this creates N long-lived WAL readers. WAL mode handles this well, but the connection is never closed between iterations — the `finally: db.close()` only fires when the loop exits. Under load (many participants, long polls), this is a connection-per-session resource hold. Not a correctness bug with WAL, but worth noting for deployments with many simultaneous participants.

8. **[warning]** `server/trio_server.py:118-183` — `export_conversation` silently returns `None` on any exception (bare `except Exception: return None`). The caller in `trio_end` only checks `if log_path` before reporting the path. If the export fails (disk full, permission error, encoding issue), `trio_end` returns `{"ok": True, "log_file": null}` with no explanation. Conversation data is committed to the DB but the markdown export is silently lost.

9. **[note]** `setup.sh:79-94` — WSL is not explicitly handled. Under WSL, `uname -s` returns `Linux`, so `PLATFORM` is set to `linux` and the native path is passed as a POSIX path. This is correct for WSL2 (Claude Code running inside WSL), but incorrect if Claude Code is running on the Windows host while setup.sh is run from WSL. The comment on line 4 lists WSL as supported, but the code has no WSL-specific path conversion. Worth documenting the assumption (both sides of the boundary must agree on which side Claude Code lives).

10. **[note]** `setup.sh:58` — `BASH_SOURCE[0]` is a bash-specific array syntax. The shebang is `#!/usr/bin/env bash` so this is correct, but MSYS2 ships `/usr/bin/bash` not `/usr/bin/env bash` in all configurations. On a stripped MSYS2 environment without `env`, the shebang fails before `BASH_SOURCE` is even evaluated. Minor: document that `bash setup.sh` (explicit invocation) is safer than `./setup.sh` on Windows.

11. **[note]** `server/trio_server.py:553` — The `trio_claim` atomicity relies on the SQLite `UPDATE ... WHERE status = 'open'` conditional update pattern. This is correct — SQLite serializes writes and `rowcount` accurately reflects the race. The WAL pragma is set correctly. The construction is sound. Noted as a positive: the atomic claim is properly implemented without application-level locking.

12. **[note]** `server/trio_server.py` — No `+x` bit is needed. The server is invoked as `python <path>`, not as a direct executable, so file permissions on the `.py` file are irrelevant for functionality. `setup.sh` correctly does not attempt to `chmod` it.

**Summary:** The setup script has one silent correctness bug (single-quoted variable in Python heredoc means the allowlist step writes to a literal path `$SETTINGS_JSON`, not the real settings file) and one missing enforcement step (Python version is reported but not validated against the 3.10+ requirement). The server itself is cleanly constructed with correct WAL concurrency and atomic claim semantics.
