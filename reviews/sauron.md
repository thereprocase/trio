**Findings:**

1. **[warning]** `trio_server.py:266-276` — TOCTOU race in `trio_connect` join path. The member count SELECT and the subsequent INSERT are not inside a transaction with SERIALIZABLE isolation. Two agents calling `trio_connect` simultaneously could both read count=19 and both insert, exceeding MAX_MEMBERS. SQLite's default `DEFERRED` transactions only acquire a write lock at the first write statement, so the count read is not protected. **Fix:** Use `BEGIN IMMEDIATE` before the count check, or add a trigger/check constraint on the members table, or re-check count after insert and rollback on violation.

2. **[warning]** `trio_server.py:491-496` / `trio_wait.py:95-109` — Watermark advances to global MAX(id) but the poll query filters `member_id != ?`. If member A sends msg 10, then member B sends msg 11, then member A polls: A sees msg 11 (from B), and watermark advances to 11. Correct. But consider: A sends msg 10, A polls immediately (no new messages from others), watermark stays at the connect-time value. Then B sends msg 11. A polls, sees msg 11, watermark advances to 11. This works. However, if A sends msg 10, then A sends msg 12 (no one else sent 11 because autoincrement is sequential per-connection), then B sends msg 13 — A's watermark is still at whatever it was before A's sends because `trio_send` sets watermark to the message A just sent (line 414: `last_read = msg_id`). So `trio_send` correctly advances A's own watermark past A's own messages. This interaction is actually correct on closer inspection. **Downgraded to note** — the dual watermark-advance logic (in send and in poll) is correct but fragile. If either path is modified independently, messages could be skipped or double-delivered. A comment explaining the invariant would help.

3. **[warning]** `trio_server.py:284-289` / `trio_server.py:302-307` — The join message is posted with the joiner's `member_id`, meaning the joiner's own `trio_poll` will filter it out (since `member_id != ?`). The joiner never sees their own join message in poll results. This is consistent but means if another member joins *between* the joiner's connect and first poll, the joiner will see the other member's join but not their own. This is probably intentional, but it creates an asymmetry: the joiner's `recent_messages` from connect (line 317) *does* include their own join message (no member_id filter on that query). So the joiner sees their join once in connect, never again. Others see it in poll. Consistent, just undocumented.

4. **[warning]** `trio_server.py:258-289` — No mechanism to deactivate a member (`active` is set to 1 on join, never set to 0). The `active` column is read in member counts and status displays, but there is no `trio_leave` or timeout-based deactivation. A member who crashes or disconnects stays `active=1` forever. The `last_seen` heartbeat is updated but never used to reap stale members. This means `MAX_MEMBERS` slots are consumed permanently. **Fix:** Either add a `trio_leave` tool, or add reaping logic (e.g., members not seen in 10 minutes marked `active=0`), or remove the `active` column and count by presence alone.

5. **[note]** `trio_server.py:46-48` — Member ID collision space is 36^6 = 2,176,782,336. With MAX_MEMBERS=20 per channel, birthday-paradox collision probability per channel is ~P = 1 - e^(-n(n-1)/2N) ≈ 9.2e-8 per channel at full occupancy. Acceptable for the use case. No uniqueness constraint beyond the (id, channel) primary key, so cross-channel collisions are irrelevant (same member_id in different channels is fine).

6. **[note]** `trio_server.py:551-555` — Task claim uses `UPDATE ... WHERE status = 'open'` which is atomic under SQLite's single-writer model. This is the correct pattern — no TOCTOU race here. The rowcount check correctly detects both "doesn't exist" and "already claimed" cases.

7. **[note]** `trio_server.py:623-627` — Task completion uses `UPDATE ... WHERE claimed_by = ? AND status = 'claimed'`, correctly preventing double-completion and ensuring only the claimer can complete. The error reporting on lines 636-638 correctly distinguishes "not your task" from "wrong status."

8. **[note]** `trio_wait.py:44` — The background poller runs an infinite loop with no exit condition other than finding messages or channel end. If the channel is deleted via `trio_cleanup` while a poller is running, the channel disappears and the poller returns `channel_gone` (line 61). Correct. But if the database file itself is deleted or corrupted, the `get_db()` call on line 45 will throw an unhandled exception. This is an edge case — the poller is a background script and crash-on-corrupt is acceptable behavior.

9. **[note]** `trio_server.py:829-848` — `trio_cleanup` deletes channel data without checking if members are actively polling. Active pollers in `trio_poll` or `trio_wait.py` will either get empty results (watermark past all messages) or `channel_gone` on next iteration. This is acceptable — cleanup is an admin operation — but a race exists where a poller reads the member record, then cleanup deletes it, then the poller tries to update watermark on a deleted row. The UPDATE would silently affect 0 rows, and the poller would re-read member as None, returning `channel_gone`. Correct by accident.

10. **[warning]** `trio_server.py:55-111` — `get_db()` runs `CREATE TABLE IF NOT EXISTS` on every call. Every tool invocation pays the cost of four DDL statements. These are no-ops after first creation, but each still acquires a write lock briefly under WAL mode. Under high concurrency (many pollers hitting the DB every 2-3 seconds), this creates unnecessary lock contention. **Fix:** Check for table existence once (e.g., via a module-level flag or by catching the first query's "no such table" error), or move schema creation to a dedicated `init_db()` called once at startup.

11. **[note]** `trio_server.py:57` — `timeout=10` on `sqlite3.connect` is the *connection* timeout (how long to wait for the DB file lock), while `busy_timeout=5000` (line 59) is the *statement* retry timeout. These are different knobs. The 10-second connect timeout is generous; the 5-second busy timeout is reasonable for WAL mode. No issue, just documenting the interaction.

12. **[note]** `trio_server.py:739-788` — `trio_end` does not post a "[ended]" message to the message log before setting channel status. Other members learn about the end via the status check in poll, not via a message. This means the conversation export (line 773) won't contain an explicit end marker — the log just stops. Minor UX gap.

**Summary:** The state machines and data flow are fundamentally sound — task claiming is atomic, watermarks advance correctly, and channel lifecycle transitions are properly guarded. The main structural weakness is the TOCTOU race in member-count enforcement during connect, and the inability to reclaim member slots from disconnected participants.
